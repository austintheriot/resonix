KEY FINDINGS AT A GLANCE
================================================================================

CRITICAL INSIGHT #1: Zero Per-Block Allocation
Pure Data's core design principle is that the audio callback must NEVER
allocate memory. All buffers and structures are pre-allocated at graph
compile time. This is non-negotiable for reliable real-time performance.

CRITICAL INSIGHT #2: Power-of-2 Buffer Sizing
Signal buffers are allocated in powers of 2 (128, 256, 512, etc.).
This eliminates heap fragmentation, enables O(1) pool lookup, and
provides deterministic memory behavior over long sessions.

CRITICAL INSIGHT #3: The Compiled DSP Chain
Instead of walking a graph at runtime, Pd compiles a flat sequence of
function pointers. This is cache-friendly, has no dispatch overhead,
and enables deterministic execution order.

CRITICAL INSIGHT #4: Borrowed Signals & Reference Counting
Signals can share buffers through reference counting. When refcount=0,
signals are marked reusable. This enables efficient multi-tap sharing
without copying, critical for complex node configurations.

CRITICAL INSIGHT #5: I/O Isolation Through Global Buffers
All audio I/O funnels through two pre-allocated global buffers:
st_soundin and st_soundout. Only adc~ and dac~ touch these. This
separates I/O concerns from processing logic cleanly.

ARCHITECTURAL PATTERNS TO ADOPT FOR RESONIX
================================================================================

PATTERN 1: Sized Allocation Tracking
✓ Every malloc includes explicit size: getbytes(size)
✓ Every free includes size: freebytes(ptr, size)
✓ Enables leak detection, memory profiling, debug hooks
✓ Critical for long-running services

PATTERN 2: Pre-Allocated Signal Buffers with Reuse Pools
✓ Allocate at graph compile time, not block time
✓ Use power-of-2 sizing: 34 size buckets (log2(1) to log2(2^33))
✓ Maintain per-size freelists for rapid reclamation
✓ Reference count to prevent premature reuse

PATTERN 3: Compiled DSP Chain Execution
✓ Build flat operation sequence at graph compile time
✓ Each operation is (function_ptr, arg1, arg2, ..., arg3)
✓ Execute via pointer chasing with clear termination
✓ Cache-friendly, deterministic, easy to profile

PATTERN 4: Separate Message & Signal Domains
✓ Message domain: event-driven, runs between blocks
✓ Signal domain: block-based, runs during block processing
✓ Objects can implement both simultaneously
✓ Control messages take effect at block boundaries

PATTERN 5: Abstract I/O Interface
✓ Multiple implementations (JACK, ALSA, PortAudio, etc.)
✓ Single public interface (sys_send_dacs, sys_open_audio, etc.)
✓ Selected at runtime via configuration
✓ Core code is API-agnostic

PATTERN 6: Opaque API for Stability
✓ Public API exposes only pointers, hides struct definitions
✓ Externals access via functions, not direct member access
✓ Allows internal changes without breaking external code
✓ Paired with version checking for compatibility

PATTERN 7: Multi-Rate Processing with block~
✓ Prolog: checks phase, skips if not time to run
✓ Block content: normal DSP code
✓ Epilog: handles reblocking (up/downsampling)
✓ Enables hierarchical time scales and nesting

PATTERN 8: Class Registration with Symbol Lookup
✓ Objects export *_setup() functions
✓ Methods registered via class_addmethod()
✓ Fast paths for common messages (bang, float, symbol, list)
✓ Generic hash-table lookup for user-defined messages

ARCHITECTURAL DECISIONS TO AVOID
================================================================================

AVOID #1: Circular Signal Dependencies
- Pd has NO cycle detection; circular graphs crash silently
- User's responsibility to avoid cycles
- Recommendation: Add explicit cycle detection in Resonix

AVOID #2: Dynamic Graph Changes During DSP
- Pd requires turning off DSP to modify graph
- Graph recompilation has latency
- Recommendation: Support live editing with atomic chain swaps,
  or require DSP off for edits (simpler but less user-friendly)

AVOID #3: Per-Block Memory Allocation
- NEVER malloc in the audio callback
- Leads to real-time violations, glitches, unpredictability
- Recommendation: Enforce via design (zero alloc in hot path)

AVOID #4: Variable Block Sizes Without Negotiation
- Automatic reblocking has overhead
- Pd auto-promotes scalars to signals (wasteful)
- Recommendation: Mandate uniform block size or explicit negotiation

AVOID #5: Direct Heap Fragmentation
- Don't use malloc freely for signal buffers
- Use power-of-2 sizing to enable efficient reuse
- Recommendation: Implement per-size freelists

TOP 10 INSIGHTS FOR RESONIX DESIGN
================================================================================

1. BUFFER MANAGEMENT IS FOUNDATIONAL
   The difference between Pd's stability and unstable audio systems is
   buffer management. Adopt sized allocation, power-of-2 sizing, and
   deferred cleanup. This is 80% of the battle for reliability.

2. COMPILE, DON'T INTERPRET
   Pre-building the DSP chain gives you:
   - Cache locality (linear memory access)
   - Zero dynamic dispatch overhead
   - Deterministic timing
   - Easy profiling/optimization
   
   Worth the complexity cost.

3. I/O ISOLATION IS CRITICAL
   Keep hardware I/O decoupled from processing logic via global buffers
   and adc~/dac~-like objects. This enables:
   - Flexible channel routing
   - Multi-device support
   - Easy testing/mocking

4. SEPARATE CONCERNS: MESSAGE vs SIGNAL
   Don't try to do everything in the signal callback. Use message
   callbacks (running at block boundaries) for parameter updates.
   This simplifies both domains.

5. REFERENCE COUNTING SCALES
   Don't allocate/deallocate signals per-block. Use refcounting with
   deferred cleanup (mark reusable, clean up at compile time).
   Supports complex object destruction patterns.

6. ABSTRACT YOUR I/O LAYER
   Support multiple audio APIs (JACK, PortAudio, PulseAudio, etc.)
   through a uniform interface. This isn't hard if you do it from day 1.

7. SIZED ALLOCATIONS ARE ESSENTIAL
   Every malloc must include explicit size. This enables leak detection,
   memory profiling, and debug hooks. Non-negotiable for services.

8. FORWARD COMPATIBILITY IS HARD
   Pd's 25-year API stability is impressive but achieved through
   conservative changes and opaque types. Plan for API versioning.

9. LOCK-FREE COMMUNICATION IS WORTH IT
   Pd uses ringbuffers for GUI→core communication from other threads.
   Avoids locks during audio processing. Highly recommended.

10. TESTING THE AUDIO CALLBACK IS TRICKY
    Pre-allocate everything, so you can call dsp_tick() in unit tests
    without worrying about side effects. This architecture supports
    thorough testing of realtime code.
